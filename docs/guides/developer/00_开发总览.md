# TestPipe 开发总览

## 1. 文档定位

本目录面向框架开发者和扩展开发者，目标是回答三个问题:

1. 什么能力应该写成 `TestOp`
2. 什么能力应该写成基础 `Action / API Provider`
3. 如何在不破坏框架一致性的前提下扩展系统

推荐阅读顺序:

1. [软件需求说明书](../../requirements/02_软件需求说明书.md)
2. [Pipeline API](../../api/pipeline_api.md)
3. [自定义测试算子](01_自定义测试算子.md)
4. [自定义API与Action扩展](02_自定义API与Action扩展.md)

---

## 2. 核心开发原则

- **单一执行模型**: 所有测试执行都由 `TestEngine` 驱动。
- **单一真相源**: `PipelineSpec / OpSpec / CaseSpec` 是统一约束模型。
- **副作用集中**: 外部命令、SSH、文件传输、资源获取必须经过统一 Action 层。
- **可追踪**: 所有动作要能进入 step 日志和 `reproduce.sh`。
- **弱化魔法**: 允许 DSL 提升易用性，但不要牺牲结构透明度。

## 3. 扩展点划分

### 3.1 什么时候写 TestOp

适用于:

- 一个稳定、可复用的测试步骤
- 有清晰输入输出
- 可以成为 Pipeline 中的节点

典型例子:

- `ATCCompile`
- `Transfer`
- `Inference`
- `AccuracyCheck`

### 3.2 什么时候写 API / Action Provider

适用于:

- 多个算子都会用到底层能力
- 更偏“基础设施能力”而不是业务测试步骤
- 需要统一 tracing、重试、超时、路由

典型例子:

- `HostExecProvider`
- `DeviceExecProvider`
- `TransportProvider`
- `HTTPProvider`

### 3.3 什么时候写辅助库

适用于:

- 纯数据处理
- 无外部副作用
- 不需要进入运行时追踪

典型例子:

- 参数归一化
- 输出解析
- 精度计算工具

---

## 4. 强制约束

- 不允许在 `TestOp` 内直接调用 `subprocess.run`
- 不允许在 `TestOp` 内直接建立裸 `paramiko` 连接
- 不允许在多个文档中同时维护不同版本的接口契约
- 不允许以 JSON/ONNX 作为主执行格式覆盖 Python DSL + Spec 模型

## 6. 开发顺序建议

1. 先定义 `Spec` 模型。
2. 再实现 `ActionRunner` 和 `TestEngine`。
3. 再补内置 `TestOp`。
4. 最后做导出、文档和批量数据支持。

这样可以避免先写大量算子，最后发现运行时模型不稳定而返工。

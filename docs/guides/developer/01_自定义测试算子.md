# 开发指南 - 自定义测试算子

## 1. 适用范围

本文档用于指导如何在 TestPipe 中新增一个可维护、可追踪、可复用的 `TestOp`。

`TestOp` 的定位不是“随便写一段测试逻辑”，而是:

- Pipeline 中可编排的稳定测试步骤
- 有强类型输入输出契约
- 能被统一执行引擎调度
- 能被统一日志、工件和复现系统感知

---

## 2. 设计要求

每个 `TestOp` 必须满足以下要求:

### 2.1 有稳定的契约

必须显式声明:

- `op_type`
- `version`
- `category`
- `inputs`
- `outputs`
- `attrs`

### 2.2 有清晰的边界

一个算子只负责一个测试步骤，不要把多个阶段逻辑堆在一个算子里。

错误示例:

- 一个算子同时完成 Git 拉取、模型编译、文件传输、板端推理、精度比对

正确示例:

- `ResourceFetch`
- `ATCCompile`
- `Transfer`
- `Inference`
- `AccuracyCheck`

### 2.3 不直接操作底层系统

算子内禁止直接使用:

- `subprocess.run`
- 裸 `paramiko`
- 随意创建远程连接

必须通过 `context.actions` 或 `context.host/device/transfer/resource` 执行。

---

## 3. 推荐实现模式

```python
from testpipe.core import TestOp, register_op
from testpipe.spec import OpSpec, PortSpec, AttrSpec


@register_op
class ATCCompileOp(TestOp):
    spec = OpSpec(
        op_type="ATCCompile",
        version="1.0",
        category="compile",
        inputs=[
            PortSpec(name="model_path", type="artifact:path", required=True, description="待编译模型路径"),
            PortSpec(name="soc_version", type="string", required=True, description="目标芯片版本"),
        ],
        outputs=[
            PortSpec(name="om_path", type="artifact:path", required=True, description="生成的 OM 文件路径"),
        ],
        attrs=[
            AttrSpec(name="framework", type="int", required=False, default=5, description="ATC framework 参数"),
            AttrSpec(name="timeout", type="int", required=False, default=600, description="命令超时时间"),
        ],
    )

    def execute(self, context):
        model_path = context.inputs.require("model_path")
        soc_version = context.inputs.require("soc_version")

        framework = context.attrs.get("framework", 5)
        timeout = context.attrs.get("timeout", 600)
        output_path = context.step_dir / "model"

        result = context.host.exec(
            [
                "atc",
                f"--model={model_path}",
                f"--framework={framework}",
                f"--output={output_path}",
                f"--soc_version={soc_version}",
            ],
            timeout=timeout,
            capture_output=True,
        )

        context.artifacts.add_file("compiled_model", f"{output_path}.om")

        return {
            "om_path": f"{output_path}.om",
        }
```

## 4. 执行上下文使用规范

建议把上下文能力分成以下几类:

- `context.inputs`: 读取输入
- `context.attrs`: 读取算子属性
- `context.host`: 在 Host 执行动作
- `context.device`: 在 Device 执行动作
- `context.transfer`: 执行传输动作
- `context.resource`: 获取 Git/本地/URL 资源
- `context.artifacts`: 记录产物
- `context.logger`: 记录日志

### 4.1 输入读取

优先使用强约束读取接口:

```python
model_path = context.inputs.require("model_path")
```

避免直接对共享 `dict` 取值。

### 4.2 动作执行

所有外部副作用必须进入统一 Action Runner:

```python
result = context.device.exec("bash run_infer.sh", timeout=300)
remote_path = context.transfer.put(local_path, "/data/model.om")
```

### 4.3 工件登记

凡是对排障有价值的产物，都要进入工件目录:

```python
context.artifacts.add_file("om", om_path)
context.artifacts.add_file("infer_log", infer_log_path)
```

## 5. 日志与错误处理

### 5.1 日志原则

- `info` 记录阶段性动作
- `debug` 记录关键参数和详细上下文
- `warning` 记录可恢复问题
- `error` 记录最终失败原因

### 5.2 异常原则

算子抛出的异常应为框架内异常，不要直接把底层原始异常裸抛到上层。

推荐:

```python
raise OpExecutionError(
    op_name=self.spec.op_type,
    message="ATC 编译失败",
    cause=result.error,
)
```

### 5.3 teardown 原则

如果算子需要资源清理:

- `teardown` 必须幂等
- `teardown` 必须允许失败但不覆盖主异常

---

## 6. 测试要求

每个新算子至少应具备三类测试:

### 6.1 契约测试

- 输入输出定义完整
- 必填属性是否正确
- 默认值是否合法

### 6.2 执行测试

- 成功路径
- 超时路径
- 失败路径

### 6.3 追踪测试

- step 日志是否生成
- 动作是否被 TraceRecorder 记录
- 产物是否写入工件目录

---

## 7. 反模式

以下写法应避免:

### 7.1 巨型算子

一个算子做完整端到端流程，会导致:

- 难复用
- 难可视化
- 难追踪
- 难局部重试

### 7.2 隐式输入输出

不要依赖约定俗成的全局变量或隐藏上下文字段。

### 7.3 直接访问底层基础设施

不要在算子里绕过 `ActionRunner` 直接访问 SSH、Docker、NFS。

### 7.4 将调试逻辑写进主路径

调试信息应该通过日志、trace 和 artifacts 导出，而不是把大量 debug 分支写进执行代码。

---

## 8. 开发检查清单

提交新的算子前，至少确认:

- 已声明 `OpSpec`
- 输入输出命名清晰
- 未直接调用裸副作用 API
- 失败信息可读
- 关键产物已归档
- 单元测试覆盖成功和失败路径
- 示例 Pipeline 能引用该算子

---

## 9. 推荐命名

- 类名: `XxxOp`
- `op_type`: `Xxx`
- 文件名: `xxx_op.py`
- 输出端口: 尽量带语义，如 `compiled_om_path`，避免泛化命名 `result`

这样在大规模 Pipeline 中更利于维护和审查。

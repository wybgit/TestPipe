# TestPipe 软件设计需求说明书

## 1. 文档定位

本文档定义 TestPipe 的**目标能力、架构约束、核心对象模型和 MVP 边界**，用于指导后续架构设计、代码实现和文档维护。

它不是原始需求的简单汇总，而是在以下材料基础上的收敛版本:

- [原始需求](00_原始需求.md)
- [测试场景](01_测试场景.md)
- [文档首页](../README.md)

---

## 2. 产品定位

TestPipe 是一个面向 NPU 软件栈的测试编排与执行框架，用于覆盖:

- 端到端模型转换与推理测试
- 算子级功能与精度测试
- API / AW 调用链路测试
- 批量数据驱动的回归测试

其核心定位是:

- 用 `Pipeline` 抽象测试流程
- 用 `TestOp` 抽象测试步骤
- 用 `CaseSpec / Dataset` 承载测试数据
- 用统一引擎执行、追踪和沉淀结果

---

## 3. 设计目标

### 3.1 必须满足的目标

1. **流程和数据解耦**  
   测试流程定义与测试用例数据分离，同一个 Pipeline 可复用于多个场景。

2. **单点与端到端兼顾**  
   同时支持算子测试、模型转换测试、板端推理测试和 API 接口测试。

3. **环境能力统一**  
   Host / Device / Docker / SSH / 文件传输等基础设施能力由统一运行时管理。

4. **强约束可扩展**  
   支持扩展新的 `TestOp` 和底层 Provider，但必须遵循统一契约。

5. **可追踪可复现**  
   任何一步失败都必须能定位到具体 step、输入、动作和产物，并生成复现脚本。

6. **可导出可理解**  
   Pipeline 的结构、参数和能力边界能导出为图、Schema 和文档，便于人和 LLM 共同消费。

7. **LLM 原生可编程**  
   框架应天然支持大模型参与测试节点生成、测试构图、用例生成、用例检查、用例执行和结果分析，并通过统一模板和 skill 接口对这些过程进行约束。

### 3.2 非目标

MVP 阶段不追求:

- Web UI
- 分布式调度平台
- 把 ONNX 作为主执行格式
- 任意 Python 动态控制流都可无损导出

## 4. 核心设计原则

### 4.0 当前冻结决策

自 2026-04-11 起，当前实现阶段冻结以下 3 个决定:

1. **`PipelineSpec` 是唯一执行真相源**  
   Python DSL 只负责编写与编译，JSON / ONNX / DOT 均不是主执行格式。

2. **`TestEngine` 是唯一执行入口**  
   不允许并行维护第二套主 runtime，也不允许 `Pipeline.run()` 绕过引擎。

3. **所有外部副作用统一经过 `ActionRunner`**  
   `TestOp` 不允许直接调用 `subprocess`、裸 SSH 或其他绕过追踪的底层接口。

### 4.1 单一真相源

框架必须围绕统一的 Spec 层构建:

- `OpSpec`
- `PipelineSpec`
- `CaseSpec`
- `EnvProfile`

任何执行、导出、文档和 Schema 生成，都应以 Spec 为输入。

### 4.2 单一执行引擎

系统只允许一套主执行模型:

- `Pipeline` 负责编排
- `PipelineCompiler` 负责编译为 `PipelineSpec`
- `TestEngine` 负责执行

不允许并存多套主 runtime。

### 4.3 强类型契约

`TestOp` 必须显式声明输入、输出和属性，框架在注册和加载阶段进行校验。

### 4.4 副作用集中

所有外部副作用必须经过统一 Action 层，不允许直接在 `TestOp` 中绕过运行时访问底层系统。

### 4.5 可观测优先

日志、trace、工件目录和复现脚本不是附加能力，而是执行模型的组成部分。

## 5. 总体架构

推荐采用五层模型:

### 5.1 Authoring 层

- Python DSL 定义 Pipeline
- YAML / CSV / Excel 定义测试输入

### 5.2 Spec 层

- `OpSpec`
- `PipelineSpec`
- `CaseSpec`
- `EnvProfile`

### 5.3 Runtime 层

- `PipelineCompiler`
- `ExecutionPlanner`
- `TestEngine`
- `ResultEvaluator`
- `ArtifactStore`

### 5.4 Infra 层

- `HostExecutor`
- `DeviceExecutor`
- `Transporter`
- `ResourceResolver`
- `TraceRecorder`

### 5.5 Export 层

- DOT 导出
- ONNX 快照导出
- JSON Schema 导出
- Markdown / 站点文档导出

### 5.6 LLM Enablement 层

- Template Registry
- Skill Registry
- Prompt / Schema Exporter
- LLM Workflow Orchestrator

## 6. 主表示与执行模型

### 6.1 主表示

推荐定义:

- **编写入口**: Python DSL
- **执行真相源**: `PipelineSpec`
- **导出格式**: DOT / ONNX / JSON Schema / Markdown

### 6.2 不推荐模型

以下方式不应成为执行真相源:

- 直接执行 JSON Pipeline
- 直接执行 ONNX Pipeline
- 让 `Pipeline.run()` 自行绕过统一引擎

### 6.3 Python Pipeline 的边界

Python Pipeline 应被视为**构图 DSL**，而不是任意逻辑容器。

允许:

- 添加节点
- 定义显式边
- 声明阶段
- 声明结构化条件和循环节点

不建议:

- 把大量控制逻辑直接写进 `forward()` 并作为主执行路径

## 7. 核心对象模型

### 7.1 OpSpec

用于定义单个算子的静态契约:

- `op_type`
- `version`
- `category`
- `inputs`
- `outputs`
- `attrs`

### 7.2 PortSpec

用于定义输入输出端口:

- `name`
- `type`
- `required`
- `description`
- `artifact_kind`

### 7.3 AttrSpec

用于定义算子属性:

- `name`
- `type`
- `required`
- `default`
- `enum`
- `description`

### 7.4 PipelineSpec

用于定义测试图:

- Pipeline 名称和描述
- 输入输出
- 节点列表
- 显式边关系
- 节点属性
- 阶段信息

### 7.5 CaseSpec

用于定义单个测试用例:

- case id / name
- pipeline 引用
- inputs
- expected
- tags / priority / timeout

### 7.6 EnvProfile

用于定义运行环境:

- Host 执行配置
- Device 连接配置
- 传输策略
- 资源解析策略

---

## 8. 运行时要求

### 8.1 PipelineCompiler

职责:

- 将 Python DSL 编译为 `PipelineSpec`
- 检查命名冲突
- 检查端口依赖
- 输出用于导出和执行的统一结构

### 8.2 ExecutionPlanner

职责:

- 做拓扑排序
- 检查断边和环
- 决定执行顺序
- 为后续并行执行保留扩展点

### 8.3 TestEngine

职责:

- 初始化运行上下文
- 注入环境和 Provider
- 驱动 step 执行
- 汇总结果
- 输出日志、工件和复现脚本

### 8.4 ResultEvaluator

职责:

- 校验 expected
- 统一判定 pass / fail / error
- 生成 summary

---

## 9. Action 与 Provider 约束

### 9.1 Action 层职责

Action 层承载所有副作用操作，例如:

- Host 命令执行
- Device 命令执行
- 文件传输
- 资源拉取
- 断言比对

### 9.2 强制要求

- 所有外部副作用必须经过 Action 层
- Action 必须统一记录 trace
- Action 必须支持 timeout、错误码和标准响应

### 9.3 Provider 模式

基础设施能力采用注册式扩展:

- `ApiRegistry`
- `ActionRegistry`

不建议通过直接修改核心类构造函数来新增能力。

## 10. 环境与资源调度要求

### 10.1 Host 执行环境

至少支持:

- 本机执行
- Docker 执行

### 10.2 Device 执行环境

至少支持:

- SSH
- 为 Telnet 预留扩展位

### 10.3 传输策略

至少支持:

- SFTP
- NFS
- 自动路由策略

自动路由应基于:

- 文件大小
- 远端存储限制
- 全局配置

### 10.4 资源来源

资源需支持:

- 本地路径
- Git 仓库
- URL
- 框架内产物引用

## 11. 数据驱动模型

### 11.1 数据载体

框架应支持:

- YAML: 适合单个或少量复杂场景
- CSV / Excel: 适合海量算子与参数批量回归

### 11.2 模型拆分

建议拆为:

- `CaseSpec`
- `DatasetLoader`
- `CaseExpander`
- `ParameterResolver`

### 11.3 覆盖优先级

推荐统一为:

1. Pipeline 默认值
2. 环境配置值
3. 数据集行值
4. CLI 覆盖值

## 12. 可观测性与复现

### 12.1 Case 级工作空间

每个用例必须拥有独立目录:

```text
runs/
  <case_id>_<timestamp>/
    spec.yaml
    summary.json
    reproduce.sh
    steps/
    artifacts/
```

### 12.2 Step 级日志

每个 step 至少输出:

- `stdout.log`
- `stderr.log`
- `step.json`

### 12.3 Trace 记录

每个动作应记录:

- 动作类型
- 执行位置
- 输入参数
- 返回码
- 耗时
- 关联产物

### 12.4 复现脚本

执行结束后自动生成 `reproduce.sh`，用于最低层复现和排障。

## 13. 可视化与文档导出

### 13.1 DOT / ONNX

DOT 和 ONNX 的定位是:

- 图审查材料
- 文档产物
- 结构展示快照

不作为主执行格式。

### 13.2 Schema 导出

框架应支持从 Spec 导出:

- JSON Schema
- Markdown 参数说明
- LLM Prompt 模板素材

### 13.3 Template 导出

框架应支持导出以下模板，供用户填写后直接交给 skill 使用:

- `TestOp Template`
- `Pipeline Template`
- `Case Template`
- `Case Check Template`
- `Run Template`
- `Result Analysis Template`

模板既要适合人工填写，也要适合大模型读取和补全。

### 13.4 Skill 体系导出

框架应定义并维护一组与模板对应的标准 skills，例如:

- 节点生成 skill
- 构图生成 skill
- 用例生成 skill
- 用例检查 skill
- 用例执行 skill
- 结果分析 skill

每个 skill 至少需要声明:

- 适用场景
- 输入模板
- 输出产物
- 调用前置条件
- 与框架对象模型的映射关系

### 13.5 文档站点

文档内容应围绕:

- 算子能力说明
- 输入输出契约
- 参数表
- 示例用例
- 图示
- 常见错误
- 模板填写说明
- skill 调用说明

而不是只依赖 autodoc 输出类方法列表。

## 14. MVP 边界

### 14.1 推荐 MVP 主路径

MVP 只打通以下链路:

- Python DSL -> PipelineSpec -> TestEngine
- YAML TestCase -> 单 Pipeline 执行
- Host 本机 + Device SSH + SFTP
- case 级目录 + step 级日志 + reproduce.sh

当前基础开发阶段进一步收敛为:

- 先实现 `Host 本机执行`
- 先打通 `YAML -> PipelineSpec -> TestEngine -> runs/`
- 先提供最小内置算子和示例 Pipeline
- 远端 Device / SSH / SFTP 在骨架稳定后再接入

### 14.2 推荐优先场景

首选实现:

- GE / ATC 模型转换 -> 文件传输 -> 板端推理 -> 精度比对

同时建议在 MVP 中补最小 LLM 原生闭环:

- 节点模板导出
- 用例模板导出
- 用例检查 skill
- 结果分析 skill

### 14.3 MVP 暂缓项

- 单 TestCase 多 Pipeline
- 复杂动态 Pipeline 导出
- Web UI
- 大规模并行调度

## 15. 验收标准

### 15.1 架构一致性

- 只有一套主执行引擎
- 执行基于 `PipelineSpec`
- 算子契约能在注册阶段校验

### 15.2 可用性

- 能跑通 ATC E2E 样例
- YAML 用例可以引用内置 Pipeline
- 失败时能快速定位 step 和动作

### 15.3 可观测性

- 生成独立 case 目录
- 生成 step 日志
- 生成 `reproduce.sh`
- 输出 summary

### 15.4 可扩展性

- 支持新增 `TestOp`
- 支持新增 Provider
- 支持导出图和 Schema
- 支持模板与 skill 注册

### 15.5 LLM 原生能力

- 能导出标准模板
- 能将模板映射到对应 skill
- skill 输出可转换为 `OpSpec / PipelineSpec / CaseSpec`
- 用例检查和结果分析具备结构化输出

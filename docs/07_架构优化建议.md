# TestPipe 架构优化建议

## 1. 文档目的

本文档基于以下材料综合分析形成:

- 原始需求: `原始需求.md`
- 需求规格: `软件需求说明书.md`
- 测试场景: `测试场景.md`
- 当前设计文档: `docs/00_总体设计.md` ~ `docs/06_文档自动生成.md`

目标不是推翻现有方案，而是在保留核心方向的前提下，收敛设计分叉，降低实现复杂度，提高软件的健壮性、可维护性和后续扩展能力。

---

## 2. 总体判断

当前设计方向整体正确，尤其是以下几点值得保留:

- 引入 AI 编译器式的图与算子抽象
- 将测试逻辑与测试数据分离
- 使用统一 API 封装 Host / Device / 文件传输能力
- 通过图导出提升可视化和可解释性
- 为 LLM 自动生成用例和文档导出预留空间

但当前方案存在一个核心问题: **主模型不统一**。

目前文档中同时存在以下几套“主表示”:

- Python `Pipeline`
- JSON `Pipeline`
- ONNX 导出图
- `TestGraph + TestEngine` DAG 执行模型
- `Pipeline.run()` 直接执行模型

如果这些都作为一等执行路径存在，后续实现会出现:

- 规则重复定义
- 加载器和执行器行为不一致
- 文档与真实代码逐步偏离
- 可视化、复现、LLM Schema 都无法稳定落地

因此，优化的第一原则不是加功能，而是先统一表示层和执行模型。

---

## 3. 高优先级优化建议

## 3.1 统一 Pipeline 的唯一真相源

### 当前问题

当前文档同时支持:

- Python 定义 Pipeline
- JSON 定义 Pipeline
- ONNX 作为流程承载

这会导致 Pipeline 的定义、加载、执行、导出和文档生成出现多套逻辑。

### 优化建议

建议明确采用如下主线:

1. 用户使用 **Python DSL** 编写 Pipeline
2. 框架将其编译为统一的 **PipelineSpec IR**
3. 执行引擎只面向 `PipelineSpec` 执行
4. JSON / DOT / ONNX 仅作为导出格式，不作为执行真相源

### 为什么更好

- Python 编写体验更强，适合开发和复用
- IR 统一后，执行器、导出器、文档生成器、LLM Schema 都有稳定输入
- 避免“写一份 Python，再维护一份 JSON”的双轨成本

---

## 3.2 只保留一个执行引擎

### 当前问题

当前设计里既有:

- `TestGraph + TestEngine` 执行路径
- `Pipeline.run()` 直接执行路径

这本质上是两套 runtime。

### 优化建议

建议统一为:

- `Pipeline` 负责声明结构
- `PipelineCompiler` 负责把 Pipeline 编译为 `PipelineSpec`
- `TestEngine` 负责唯一执行入口
- `Pipeline.run()` 仅作为 `TestEngine.execute()` 的薄封装，或直接去掉

### 为什么更好

- 生命周期、日志、异常、追踪、资源释放全部集中
- 后续支持并行、重试、断点恢复时不会重复实现

---

## 3.3 将 Python Pipeline 从“任意代码”收敛为“构图 DSL”

### 当前问题

当前 `forward()` 设计支持:

- 条件分支
- 循环
- 动态创建算子
- Pipeline 嵌套调用

表达力很强，但这会削弱:

- 静态校验能力
- 图导出能力
- 复现脚本生成能力
- LLM 自动生成能力

### 优化建议

建议限制 Python Pipeline 的职责:

- 用于声明节点
- 用于声明边
- 用于声明阶段、条件节点、循环节点等结构化控制语义

不建议让 `forward()` 变成任意 Python 逻辑。

推荐模式:

```python
class ATCE2EPipeline(Pipeline):
    def define(self):
        self.add_step("check_env", EnvCheckOp(...))
        self.add_step("compile", ATCCompileOp(...))
        self.connect("check_env.env_ready", "compile.env_ready")
```

### 为什么更好

- 图是显式的、可检查的、可导出的
- 更符合你“像 AI 编译器构图”的初衷

---

## 3.4 用强类型契约替代松散的输入输出列表

### 当前问题

当前 `TestOp` 的输入输出只是 `List[str]`，属性也是松散字典。

这与原始需求中的“统一规范与强约束”不匹配，也不利于:

- YAML 校验
- CSV/Excel 表头校验
- 自动文档生成
- LLM Schema 导出

### 优化建议

建议定义以下核心契约模型:

```python
class PortSpec:
    name: str
    type: str
    required: bool
    description: str
    artifact_kind: str

class AttrSpec:
    name: str
    type: str
    required: bool
    default: Any
    enum: list | None
    description: str

class OpSpec:
    op_type: str
    version: str
    category: str
    inputs: list[PortSpec]
    outputs: list[PortSpec]
    attrs: list[AttrSpec]
```

### 为什么更好

- 注册阶段即可发现不合法算子
- 用例填空更清晰
- Schema 和 API 网站天然可导出

---

## 3.5 强制所有外部副作用通过统一 ActionRunner 执行

### 当前问题

当前设计虽然提出统一 API，但示例算子仍然直接使用:

- `subprocess.run`
- 直接 SSH 调用
- 直接文件读写

这会绕开 tracing、重试、日志、复现脚本生成。

### 优化建议

建议建立一层强制动作抽象:

```python
context.host.exec(...)
context.device.exec(...)
context.transfer.put(...)
context.resource.fetch(...)
context.assertions.compare(...)
```

底层统一由 `ActionRunner` 执行，并自动记录:

- 执行时间
- 执行位置
- 输入参数
- 返回码
- stdout / stderr
- 生成物路径

### 为什么更好

- `reproduce.sh` 才能真正自动生成
- 日志和复现链路不会漏
- 所有失败都能被统一处理

---

## 3.6 把环境和资源调度从 API 工具提升为一等模型

### 当前问题

原始需求里有很强的环境调度诉求:

- Host 本地 / Docker
- Device SSH / Telnet
- SFTP / NFS / Rsync
- Git / 本地 / URL 资源获取

但当前设计中的 `OpAPI` 偏工具箱式，不足以承载路由策略。

### 优化建议

建议单独引入:

- `EnvironmentProfile`
- `HostExecutor`
- `DeviceExecutor`
- `Transporter`
- `ResourceResolver`

推荐结构:

```python
class EnvironmentProfile:
    host: HostConfig
    device: DeviceConfig
    transport: TransportPolicy
    resource: ResourcePolicy
```

### 为什么更好

- 环境切换不再侵入每个算子
- 同一个 Pipeline 可以在不同环境配置下复用
- Docker/NFS 策略可以集中实现和测试

---

## 3.7 显式建设 Case 级工作空间和工件模型

### 当前问题

现在的执行上下文和工作目录设计偏简单，不足以支撑:

- 独立 case 隔离
- step 级日志
- 可复现脚本
- 失败排障

### 优化建议

建议将运行目录标准化:

```text
runs/
  <case_id>_<timestamp>/
    spec.yaml
    summary.json
    reproduce.sh
    steps/
      01_check_env/
        step.json
        stdout.log
        stderr.log
      02_compile/
        step.json
        stdout.log
        stderr.log
    artifacts/
```

### 为什么更好

- 每个用例的输入、输出、日志、复现脚本完整闭环
- 调试和问题追踪成本大幅下降

---

## 3.8 将 teardown 放入 finally，避免资源泄漏

### 当前问题

当前执行流程中，`teardown()` 更像成功路径的一部分，失败时资源可能无法释放。

### 优化建议

每个 Step 统一采用:

1. `validate`
2. `setup`
3. `execute`
4. `collect`
5. `teardown` 放入 `finally`

同时要求:

- `teardown` 失败只记录 warning
- 不覆盖主异常

### 为什么更好

- 更稳
- 更符合远程环境、挂载、临时文件、连接会话的实际清理需求

---

## 3.9 数据流连接应支持显式端口，不应只依赖同名自动连线

### 当前问题

当前设计主要通过输入输出名称自动建边。小规模好用，大规模时会带来:

- 同名冲突
- 连线不透明
- 图审查困难

### 优化建议

建议支持两种模式:

- 简写模式: 自动按同名端口连接
- 严格模式: 显式声明 `from -> to`

推荐最终内部统一成显式边:

```python
connect("compile.om_path", "infer.model_path")
```

### 为什么更好

- 可维护性更高
- 图导出更准确
- 用户查错更容易

---

## 3.10 将 TestCase 与 Dataset 解耦

### 当前问题

你的需求明确包含:

- YAML 测试用例
- CSV/Excel 海量批量测试
- 参数覆盖

如果都混进一个 `TestCaseLoader`，后期逻辑会越来越复杂。

### 优化建议

建议拆成:

- `CaseSpec`：描述结构
- `DatasetLoader`：加载 YAML / CSV / Excel
- `ParameterResolver`：处理覆盖优先级
- `CaseExpander`：展开矩阵和批量行

推荐覆盖优先级:

1. Pipeline 默认值
2. 环境配置值
3. 数据集行值
4. CLI 覆盖值

### 为什么更好

- 批量测试和单例测试能共用统一执行模型
- Excel / CSV 支持不会污染核心引擎

---

## 3.11 多 Pipeline 能力建议先降级到 TestSuite 层

### 当前问题

现在一个 TestCase 可以绑定多个 Pipeline。这个设计不是不能做，但会让:

- `expected` 变复杂
- 结果目录语义变重
- 失败归因变难

### 优化建议

MVP 阶段建议:

- 一个 `TestCase` 只绑定一个 `Pipeline`
- 多 Pipeline 组合执行放到 `TestSuite`

### 为什么更好

- 执行模型更简单
- 结果收敛更清晰
- 便于后续并行化

---

## 3.12 ONNX 更适合作为可视化快照，而不是执行格式

### 当前问题

需求中希望借助 ONNX + Netron 可视化，这是合理的。
但如果把 ONNX 当执行真相源，会引入大量不必要复杂度。

### 优化建议

建议将 ONNX 定位为:

- Graph Snapshot
- Review Artifact
- Documentation Artifact

不是执行入口。

同时建议导出时补充更多 metadata:

- 节点说明
- 参数摘要
- timeout
- 环境目标
- 产物说明
- 校验规则

### 为什么更好

- Netron 展示价值更高
- 不会把可视化格式绑架执行引擎设计

---

## 3.13 API 扩展机制要从“改主类”升级为“注册式扩展”

### 当前问题

现在自定义 API 的方式是直接修改 `OpAPI.__init__` 添加字段。

这种方式初期简单，长期会导致:

- 主类越来越大
- 扩展冲突
- 插件化困难

### 优化建议

建议改成:

```python
ApiRegistry.register("http", HTTPApiProvider)
api = context.api.get("http")
```

### 为什么更好

- 支持插件化
- 支持按需加载
- 便于隔离可选依赖

---

## 3.14 文档生成应以契约和示例为中心，而不只是 autodoc

### 当前问题

单纯从类和方法生成文档，对最终用户价值有限。

用户真正关心的是:

- 这个算子干什么
- 输入输出是什么
- 参数怎么填
- 示例 YAML / CSV 怎么写
- 对应哪张图
- 会产出什么工件

### 优化建议

文档站点建议由以下内容联合生成:

- 代码 docstring
- `OpSpec / PipelineSpec / CaseSpec`
- 示例用例
- 导出的图
- 常见错误说明

### 为什么更好

- 更适合框架用户
- 更适合 LLM Prompt / Schema 导出

---

## 4. 推荐的更优架构

建议将系统收敛为五层:

### 4.1 Authoring 层

- Python DSL 定义 Pipeline
- YAML / CSV / Excel 提供测试数据

### 4.2 Spec 层

- `OpSpec`
- `PipelineSpec`
- `CaseSpec`
- `EnvProfile`

这一层是**唯一真相源**。

### 4.3 Runtime 层

- `PipelineCompiler`
- `ExecutionPlanner`
- `TestEngine`
- `ResultEvaluator`
- `ArtifactStore`

### 4.4 Infra 层

- `HostExecutor`
- `DeviceExecutor`
- `Transporter`
- `ResourceResolver`
- `TraceRecorder`

### 4.5 Export 层

- DOT
- ONNX
- JSON Schema
- Markdown Docs
- Web Docs

---

## 5. MVP 推荐收敛范围

为了避免第一版过重，建议 MVP 只做以下闭环:

### 5.1 仅支持一个主执行路径

- Python DSL -> PipelineSpec -> TestEngine

### 5.2 仅打通一个高价值场景

- GE / ATC 模型转换 -> 板端推理 -> 精度比对

### 5.3 环境先只支持最常见组合

- Host: 本机
- Device: SSH
- Transport: SFTP

### 5.4 强制完成可观测性闭环

- case 级目录
- step 级日志
- reproduce.sh
- summary.json

### 5.5 先不在 MVP 做重功能

- 不先做 ONNX 反向执行
- 不先做复杂动态 Pipeline
- 不先做多 Pipeline 单 TestCase
- 不先做过重的 Web UI

---

## 6. 推荐落地顺序

### 第一阶段: 模型收敛

优先实现:

- `OpSpec`
- `PipelineSpec`
- `CaseSpec`
- `EnvProfile`
- `PipelineCompiler`

### 第二阶段: 最小执行链路

优先实现:

- `TestEngine`
- `ExecutionContext`
- `ActionRunner`
- `ArtifactStore`

### 第三阶段: 基础内置算子

建议优先做:

- `EnvCheck`
- `ResourceFetch`
- `ATCCompile`
- `Transfer`
- `Inference`
- `AccuracyCheck`

### 第四阶段: 导出与文档

实现:

- DOT 导出
- ONNX 快照导出
- Schema 导出
- 文档站点

### 第五阶段: 批量和高级特性

实现:

- CSV / Excel 数据集
- Docker Host
- NFS / Rsync 路由
- TestSuite
- 并行执行

## 7. 当前最值得优先拍板的设计决策

建议尽快明确以下 3 个问题:

### 决策 1: Pipeline 的主表示是什么

推荐答案:

- Python DSL 是编写入口
- PipelineSpec IR 是执行真相源
- JSON / ONNX / DOT 只是导出产物

### 决策 2: 是否允许 TestOp 直接使用 subprocess / paramiko

推荐答案:

- 不允许
- 所有外部副作用统一走 ActionRunner

### 决策 3: MVP 是否支持一个 TestCase 绑定多个 Pipeline

推荐答案:

- MVP 不支持
- 多 Pipeline 组合放到 TestSuite

---

## 8. 结论

你的框架设计已经具备成为一个高质量测试平台的雏形，问题不在于方向，而在于当前设计仍有多套表示和多条执行路径并存。

如果现在先完成以下三件事，后面的实现质量会明显更高:

1. 统一 `PipelineSpec` 作为唯一真相源
2. 强制副作用走统一 `ActionRunner`
3. 用强类型契约替代松散字典和字符串列表

这样做之后，框架会更容易做到:

- 结构稳定
- 行为可预测
- 日志和复现完整
- 易于文档化
- 易于 LLM 自动生成和消费
- 易于后续插件化和规模化扩展

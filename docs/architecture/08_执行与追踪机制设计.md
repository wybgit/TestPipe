# 执行与追踪机制设计

本文档描述当前 TestPipe 的执行链、日志和追踪落盘方式。

## 1. 执行入口

当前主入口是 CLI：

```bash
testpipe run examples/testcases/onnx_git_atc.yaml
```

执行时核心链路为：

1. `TestCaseLoader` 解析 YAML
2. `create_pipeline()` 创建 Pipeline
3. `PipelineCompiler` 生成 `PipelineSpec`
4. `TestEngine.execute()` 执行节点
5. 写出 summary、steps、resources 和图文件

## 2. TestEngine 的职责

`TestEngine` 负责：

- 生成 run 目录
- 按规划顺序执行节点
- 构造 `StepContext`
- 汇总节点输出和最终输出
- 评估 `expected`
- 导出 `pipeline_graph.dot/.pdf`
- 写出 `summary.json`

源码见 [test_engine.py](/home/wyb/AscendCode/TestPipe/testpipe/engine/test_engine.py)。

## 3. StepContext

单个节点执行时，框架会注入 `StepContext`。

主要字段：

- `inputs`
- `attrs`
- `host`
- `device`
- `transfer`
- `artifacts`
- `step_dir`
- `stdout_log_path`
- `stderr_log_path`

因此算子不需要自己管理 run 目录结构，只需专注于执行逻辑。

执行层会在进入节点前完成一次参数分流：

- 图绑定与 testcase 中属于 `spec.inputs` 的值进入 `inputs`
- 节点默认属性与 testcase 中属于 `spec.attrs` 的覆盖值合并后进入 `attrs`

## 4. trace 与日志

当前追踪由 `TraceRecorder` 和 `ActionRunner` 负责。

框架会记录：

- 命令执行
- 文件传输
- 设备动作
- stdout / stderr

当开启 `--debug` 时，会额外落盘：

- `trace.json`
- `reproduce.sh`
- `step.json`

## 5. 默认输出目录

一次执行结束后，run 目录典型结构如下：

```text
runs/
  onnx_git_atc_case_YYYYMMDD_HHMMSS/
    summary.json
    execution.log
    pipeline_graph.dot
    pipeline_graph.pdf
    resources/
    steps/
      01_fetchModelNode/
      02_compileModelNode/
      03_checkOmExistsNode/
```

## 6. 结果汇总

`summary.json` 会记录：

- `case_id`
- `pipeline`
- `status`
- `duration_ms`
- `failed_step`
- `issues`
- `outputs`

这份结果既用于 CLI 回显，也用于 `result-analyzer` 等 skill。

## 7. 与导图的关系

当前导图发生在执行阶段结束后，因此导图可以带上：

- testcase 输入值
- 节点输出值
- pipeline 最终输出值

这也是当前 DOT/PDF 图比静态结构图更有价值的原因。

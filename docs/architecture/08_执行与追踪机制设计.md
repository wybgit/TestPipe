# 执行与追踪机制设计

## 1. 文档目标

本文档定义 TestPipe 的统一执行链路，以及日志、trace、工件目录、复现脚本的落地方式。

目标是解决以下问题:

- 一个测试用例如何被执行
- 每个 step 的生命周期如何管理
- 失败时如何定位和复现
- 日志、trace、产物如何统一沉淀

---

## 2. 设计目标

- **执行链路唯一**
- **每一步都有清晰生命周期**
- **所有副作用都可追踪**
- **失败后可最低层复现**
- **日志与工件沉淀格式固定**

---

## 3. 主执行流程

推荐流程如下:

1. 加载 `CaseSpec`
2. 获取或编译 `PipelineSpec`
3. 解析 `EnvProfile`
4. 构建 `ExecutionPlan`
5. 初始化 `ExecutionContext`
6. 按拓扑顺序执行各 step
7. 汇总输出并做 expected 校验
8. 生成 `summary.json`
9. 生成 `reproduce.sh`

---

## 4. 运行目录规范

每次执行必须生成独立 case 目录:

```text
runs/
  <case_id>_<timestamp>/
    case_spec.yaml
    pipeline_spec.json
    env_profile.json
    summary.json
    reproduce.sh
    trace.json
    steps/
      01_check_env/
        step.json
        stdout.log
        stderr.log
      02_compile/
        step.json
        stdout.log
        stderr.log
    artifacts/
```

### 目录说明

- `case_spec.yaml`: 本次执行的输入快照
- `pipeline_spec.json`: 本次执行的流程快照
- `env_profile.json`: 本次执行的环境快照
- `summary.json`: 最终执行结果
- `reproduce.sh`: 最低层复现脚本
- `trace.json`: 结构化动作轨迹

---

## 5. TestEngine 设计

## 5.1 职责

`TestEngine` 负责:

- 驱动整个 case 执行
- 控制生命周期
- 初始化运行时能力
- 捕获错误并写入结果

### 不负责

- 直接实现底层命令执行
- 在内部重新解释 Pipeline 语义
- 再造一套与 `PipelineSpec` 不一致的结构

---

## 5.2 建议接口

```python
class TestEngine:
    def execute(
        self,
        case_spec: CaseSpec,
        pipeline_spec: PipelineSpec,
        env_profile: EnvProfile,
    ) -> ResultSummary:
        ...
```

---

## 6. ExecutionPlanner 设计

`ExecutionPlanner` 根据 `PipelineSpec` 生成可执行计划。

职责:

- 环检测
- 断边检查
- 输入可满足性检查
- 拓扑排序
- 生成 step 序号

输出可以是:

```python
class ExecutionStep(BaseModel):
    index: int
    node_name: str
    op_type: str
    depends_on: list[str]
```

---

## 7. Step 生命周期

每个 step 必须严格遵循以下生命周期:

1. `prepare`
2. `validate`
3. `setup`
4. `execute`
5. `collect`
6. `teardown`
7. `record`

### 7.1 prepare

准备 step 目录、logger、输入映射。

### 7.2 validate

校验:

- 输入是否齐全
- 属性是否合法
- 环境前置条件是否满足

### 7.3 setup

用于:

- 建立临时上下文
- 初始化局部资源

### 7.4 execute

执行真实业务步骤。

### 7.5 collect

收集:

- 输出端口
- 工件路径
- 统计信息

### 7.6 teardown

必须在 `finally` 中执行，负责释放资源。

### 7.7 record

写入:

- `step.json`
- stdout / stderr
- trace 片段

---

## 8. ActionRunner 设计

## 8.1 目标

统一承载所有外部副作用:

- host exec
- device exec
- transfer
- resource fetch
- http

## 8.2 统一返回格式

建议所有动作返回:

```python
class ActionResult(BaseModel):
    action_type: str
    target: str
    command: str | list[str] | None = None
    returncode: int | None = None
    stdout: str = ""
    stderr: str = ""
    started_at: str
    ended_at: str
    duration_ms: int
    artifacts: list[str] = []
```

### 好处

- 上层日志处理一致
- trace 结构统一
- 调试体验稳定

---

## 9. TraceRecorder 设计

`TraceRecorder` 用于记录结构化动作轨迹。

## 9.1 记录粒度

最小粒度是一个 Action，不是一个 step。

例如:

- `resource.fetch`
- `host.exec`
- `transfer.put`
- `device.exec`

## 9.2 建议结构

```python
class TraceEvent(BaseModel):
    step_name: str
    action_type: str
    request: dict[str, Any]
    response: dict[str, Any]
    started_at: str
    ended_at: str
```

## 9.3 输出文件

建议至少输出:

- `trace.json`
- 后续可扩展 `trace.ndjson`

---

## 10. ArtifactStore 设计

`ArtifactStore` 统一管理工件落盘和登记。

## 10.1 职责

- 在 `artifacts/` 下建目录
- 记录工件逻辑名与实际路径映射
- 支持 step 关联

## 10.2 建议接口

```python
class ArtifactStore:
    def add_file(self, logical_name: str, path: str, step_name: str | None = None):
        ...

    def add_text(self, logical_name: str, content: str, filename: str):
        ...
```

## 10.3 为什么单独抽象

否则不同算子会:

- 各自决定路径
- 各自决定命名
- 难以在结果页面统一展示

---

## 11. 日志设计

## 11.1 三层日志

建议日志分为:

- 控制台摘要日志
- step 级文件日志
- trace 级结构化日志

## 11.2 控制台日志

只输出:

- case 开始
- step 开始 / 成功 / 失败
- 结果摘要

## 11.3 step 日志

每个 step 保存:

- `stdout.log`
- `stderr.log`
- `step.json`

## 11.4 step.json 建议字段

```python
{
  "step_index": 2,
  "step_name": "compile",
  "op_type": "ATCCompile",
  "status": "passed",
  "started_at": "...",
  "ended_at": "...",
  "duration_ms": 1200,
  "inputs": ["model_path", "soc_version"],
  "outputs": ["om_path"]
}
```

---

## 12. 复现脚本设计

## 12.1 目标

让用户脱离框架也能按最底层动作复现问题。

## 12.2 生成来源

`reproduce.sh` 应由 `TraceRecorder` 的 Action 序列生成，而不是算子手写。

## 12.3 内容范围

建议包含:

- 环境变量准备
- Host 命令
- 文件传输说明
- Device 命令
- 关键工件路径说明

### 注意

不是所有传输都能 100% 自动还原，但至少应保留:

- 原始命令
- 目标位置
- 依赖文件路径

---

## 13. 异常处理策略

## 13.1 异常分类

建议区分:

- `ValidationError`
- `StepExecutionError`
- `ActionExecutionError`
- `TimeoutError`
- `EnvironmentError`

## 13.2 错误归因

summary 中至少应记录:

- 失败 step
- 失败 action
- 主错误消息
- 对应日志路径

## 13.3 teardown 错误

`teardown` 错误不应覆盖主错误，只记录为 warning。

---

## 14. Expected 校验

建议将 expected 校验独立为 `ResultEvaluator`。

### 原因

- 避免 TestEngine 过重
- 不同类型 expected 可扩展
- 方便后续支持复杂断言

### 支持形式

- 直接等值
- 区间比较
- 表达式比较
- 自定义比较器

---

## 15. 并行执行扩展位

MVP 可先串行执行，但设计上应预留:

- 独立 step 目录
- 独立 step logger
- 独立 action trace

这样后续支持并行时，无需推翻已有目录和 trace 结构。

---

## 16. 建议实现顺序

1. `ExecutionPlanner`
2. `ExecutionContext / StepContext`
3. `ActionResult / TraceEvent`
4. `TraceRecorder`
5. `ArtifactStore`
6. `TestEngine`
7. `ResultEvaluator`
8. `reproduce.sh` 生成器

---

## 17. 验收标准

- 能生成独立 case 目录
- 每个 step 都有日志和 `step.json`
- 所有副作用都进入 trace
- 失败时能定位到 step 和 action
- 能生成 `reproduce.sh`
- `summary.json` 可直接供 CLI 或报告使用

---

## 18. 结论

执行和追踪机制不是外围能力，而是框架可信度的核心。

如果这部分做得弱，后续即使 Pipeline 和算子模型再漂亮，实际落地也会遇到:

- 问题难复现
- 日志难定位
- 远程环境难排障
- 框架不敢大规模推广

因此推荐在 MVP 里优先把这部分做扎实，再扩更多场景和算子。

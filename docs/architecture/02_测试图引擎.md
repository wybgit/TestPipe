# 测试图引擎

本文档描述当前 TestPipe 中已经落地的测试图引擎实现。这里的“图引擎”指：

- `Pipeline` DSL
- `PipelineCompiler`
- `PipelineSpec`
- `ExecutionPlanner`
- `TestEngine`

共同组成的“显式构图、静态编译、拓扑执行”模型。

## 1. 当前实现总览

当前主执行链路是：

`Case YAML -> TestCaseLoader -> Pipeline -> PipelineCompiler -> PipelineSpec -> ExecutionPlanner -> TestEngine`

这意味着：

- 图结构由 Python DSL 显式声明。
- 执行引擎只消费编译后的 `PipelineSpec`。
- 节点依赖通过显式绑定和编译结果确定。
- 执行基于静态图和拓扑计划展开。

## 2. 图引擎的职责

当前图引擎负责四件事：

1. 把 Pipeline DSL 编译为稳定的静态图结构。
2. 校验节点输入绑定是否合法。
3. 基于边关系做拓扑排序并生成执行计划。
4. 按计划执行节点，汇总输出、日志、trace 和导图结果。

## 3. Authoring 层

作者在 `Pipeline.define()` 中使用的是 Authoring API：

- `Pipeline`
- `PipelineInputRef`
- `NodeHandle`
- `NodeOutputRef`
- `NodeDefinition`
- `OutputDefinition`

这层只负责“描述图”，不负责执行。

一个最小主线示例：

```python
from testpipe.core import Pipeline, register_pipeline
from testpipe.ops.assertions import PathExistsOp
from testpipe.ops.atc import ATCCompileOp
from testpipe.ops.resource import ResourceFetchOp


@register_pipeline
class OnnxGitAtcPipeline(Pipeline):
    def define(self) -> None:
        self.set_stage("prepare")
        fetch_model = self.add_node("fetchModelNode", ResourceFetchOp())

        self.set_stage("compile")
        compile_model = self.add_node(
            "compileModelNode",
            ATCCompileOp(output_name="model.om", timeout=600),
            inputs={"model_path": fetch_model.output("model_path")},
        )

        self.set_stage("assert")
        check_om = self.add_node(
            "checkOmExistsNode",
            PathExistsOp(),
            inputs={"target_path": compile_model.output("om_path")},
        )

        self.add_output("model_path", fetch_model.output("model_path"), type="artifact:path")
        self.add_output("om_path", compile_model.output("om_path"), type="artifact:path")
        self.add_output("path_exists", check_om.output("path_exists"), type="bool")
```

## 4. 编译为 PipelineSpec

`PipelineCompiler` 会把 Authoring 层对象编译为静态结构：

- `PipelineSpec`
- `NodeSpec`
- `InputBindingSpec`
- `EdgeSpec`
- `OutputBindingSpec`

当前编译规则：

- 同一个 Pipeline 内节点名必须唯一。
- 节点输入绑定只能指向：
  - 已声明的 Pipeline 输入
  - 已存在上游节点的已声明输出
- 节点构造时的离线属性会固化到 `NodeSpec.attrs`。
- 节点到节点的显式依赖会固化到 `PipelineSpec.edges`。

## 5. 输入、属性和 testcase 的关系

这是当前实现里最关键的约束：

- `spec.inputs` 表示图上流转的值。
- `spec.attrs` 表示算子默认值或行为参数。

执行前，`TestEngine` 会把 testcase 中的节点参数按 `OpSpec` 自动分流：

- 命中 `spec.inputs` 的值进入 `StepContext.inputs`
- 命中 `spec.attrs` 的值作为在线属性覆盖，进入 `StepContext.attrs`

因此：

- 输入属于图结构的一部分。
- 属性不参与图绑定，但会影响节点执行行为。

以当前主线为例：

- `fetchModelNode.inputs = repo / branch / path`
- `fetchModelNode.attrs = model_pattern`
- `compileModelNode.inputs = model_path`
- `compileModelNode.attrs = soc_version / env_script / atc_options / output_name / timeout / framework`

## 6. 执行计划生成

`ExecutionPlanner` 基于 `PipelineSpec.edges` 做拓扑排序，生成 `ExecutionStep` 列表。

每个 `ExecutionStep` 包含：

- `index`
- `node_name`
- `op_name`
- `depends_on`

当前排序规则：

- 通过 `edges` 保证依赖节点先执行。
- 对同一层可执行节点，保持 Pipeline 中的原始声明顺序。
- 若存在环，直接报错 `pipeline contains a cycle`。

## 7. TestEngine 执行流程

### 7.1 执行入口

`TestEngine.execute(case_spec, pipeline_spec, env_profile)` 会：

1. 创建 `run_dir`
2. 创建 `ExecutionContext`
3. 写入调试快照
4. 生成执行计划
5. 逐节点执行
6. 汇总 summary 和最终输出
7. 导出 DOT/PDF 图

### 7.2 节点执行前的准备

每个节点执行前，`TestEngine` 会完成：

- 合并节点属性
- 收集节点输入
- 构造 `StepContext`
- 绑定 `HostExecutor / DeviceExecutor / TransferExecutor`

属性合并规则：

- 先取 `NodeSpec.attrs` 中的离线默认值
- 再用 testcase 中 `inputs_by_node.<node>` 的同名属性做在线覆盖

输入收集规则：

- 先解析图绑定的 Pipeline 输入和上游节点输出
- 再补充 testcase 中同名节点输入
- 最后补充仍未显式绑定但与 Pipeline 输入同名的节点输入

### 7.3 节点执行

每个节点按下面顺序执行：

1. `op.setup(step_context)`
2. `op.execute(step_context)`
3. 将输出写入 `ExecutionContext.node_outputs`
4. `op.teardown(step_context)`

如果执行失败：

- 当前节点状态记为 `failed`
- 错误写入 step 日志
- 后续节点停止执行
- 最终在 `summary.json` 中标出 `failed_step`

## 8. 运行期上下文

### 8.1 `ExecutionContext`

case 级上下文负责持有：

- `case_spec`
- `pipeline_spec`
- `env_profile`
- `run_dir`
- `trace_recorder`
- `artifact_store`
- `shared_data`
- `node_outputs`

其中：

- `shared_data` 初始来自 `CaseSpec.inputs`
- 每个节点输出会写入 `node_outputs`
- 节点输出也会同步写入 `shared_data`

### 8.2 `StepContext`

节点级上下文主要暴露：

- `inputs`
- `attrs`
- `host`
- `device`
- `transfer`
- `artifacts`
- `step_dir`
- `stdout_log_path`
- `stderr_log_path`

算子只需要围绕 `StepContext` 实现执行逻辑，不需要自行管理 run 目录结构。

## 9. 执行产物

当前执行结束后会生成：

- `summary.json`
- `summary.internal.json`
- `execution.log`
- `steps/<step>/result.json`
- `steps/<step>/execution.log`
- `steps/<step>/command.sh`
- `resources/`
- `pipeline_graph.dot`
- `pipeline_graph.pdf`

当开启 `--debug` 时，还会额外生成：

- `trace.json`
- `reproduce.sh`
- `step.json`
- `case_spec.yaml`
- `pipeline_spec.json`
- `env_profile.json`

## 10. 与导图的关系

导图不是只依赖静态结构，而是综合：

- `PipelineSpec`
- `CaseSpec`
- 节点运行输出
- Pipeline 最终输出

因此导出的 DOT/PDF 图会同时展示：

- Pipeline 输入
- 节点直输输入
- 节点属性
- 节点输出
- Pipeline 输出

## 11. 当前主线执行顺序

以 `OnnxGitAtcPipeline` 为例，当前执行顺序是：

1. `fetchModelNode`
2. `compileModelNode`
3. `checkOmExistsNode`

这条链路和当前实现完全一致，不存在额外的环境检查节点。

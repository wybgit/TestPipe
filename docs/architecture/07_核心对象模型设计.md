# 核心对象模型设计

## 1. 文档目标

本文档定义 TestPipe 的核心对象模型，统一以下问题:

- 框架中哪些对象是静态契约
- 哪些对象属于运行时
- 各对象之间如何关联
- 哪些对象可以作为导出、执行、文档生成的统一输入

本文档与 [软件需求说明书](/home/wyb/AscendCode/TestPipe/docs/requirements/02_软件需求说明书.md) 保持一致，目标是将“主模型统一”落到可实现的对象层面。

---

## 2. 设计原则

- **区分静态模型与运行时对象**
- **Spec 层是唯一真相源**
- **运行时只消费 Spec，不重新定义契约**
- **导出、文档、LLM Schema 都基于 Spec**
- **对象边界清晰，不让一个类同时承担编排、执行、追踪三类职责**

---

## 3. 对象分层

建议将核心对象分为四类:

### 3.1 Authoring 对象

用于开发者编写测试流程:

- `Pipeline`
- `TestOp`

### 3.2 Spec 对象

用于统一承载静态结构和约束:

- `PortSpec`
- `AttrSpec`
- `OpSpec`
- `NodeSpec`
- `EdgeSpec`
- `PipelineSpec`
- `CaseSpec`
- `EnvProfile`

### 3.3 Runtime 对象

用于执行和追踪:

- `ExecutionContext`
- `StepContext`
- `TestEngine`
- `ExecutionPlanner`
- `TraceRecorder`
- `ArtifactStore`
- `ResultSummary`

### 3.4 Infra 对象

用于基础设施能力:

- `HostExecutor`
- `DeviceExecutor`
- `Transporter`
- `ResourceResolver`
- `ActionRunner`

---

## 4. Spec 层设计

## 4.1 PortSpec

`PortSpec` 描述一个输入或输出端口。

建议字段:

```python
class PortSpec(BaseModel):
    name: str
    type: str
    required: bool = True
    description: str = ""
    artifact_kind: str | None = None
    default: Any | None = None
```

### 说明

- `name`: 端口名称
- `type`: 类型标识，例如 `string`、`int`、`artifact:path`
- `required`: 是否必填
- `description`: 人类可读说明
- `artifact_kind`: 若是产物，标记其类别
- `default`: 可选默认值

### 设计要求

- 输入输出都使用同一模型
- 类型信息必须可导出为 JSON Schema
- 不允许只用字符串列表代替完整端口模型

---

## 4.2 AttrSpec

`AttrSpec` 描述算子属性。

```python
class AttrSpec(BaseModel):
    name: str
    type: str
    required: bool = False
    default: Any | None = None
    enum: list[Any] | None = None
    description: str = ""
```

### 设计要求

- 支持默认值
- 支持枚举约束
- 后续可挂载 validator

---

## 4.3 OpSpec

`OpSpec` 是一个 `TestOp` 的静态契约。

```python
class OpSpec(BaseModel):
    op_type: str
    version: str
    category: str
    description: str = ""
    inputs: list[PortSpec]
    outputs: list[PortSpec]
    attrs: list[AttrSpec]
```

### 作用

- 约束算子输入输出
- 用于注册校验
- 用于生成开发文档
- 用于生成 LLM Schema

### 注册要求

注册 `TestOp` 时，框架至少检查:

- `op_type` 唯一
- 输入输出名称不冲突
- 属性定义合法
- 版本号格式合法

---

## 4.4 NodeSpec

`NodeSpec` 表示 `PipelineSpec` 中的一个节点实例。

```python
class NodeSpec(BaseModel):
    name: str
    op_type: str
    op_version: str | None = None
    attrs: dict[str, Any] = {}
```

### 说明

- `OpSpec` 描述“算子类型”
- `NodeSpec` 描述“图中的某个算子实例”

这个区分很重要，否则同类算子的不同实例无法在图中独立配置。

---

## 4.5 EdgeSpec

`EdgeSpec` 表示节点之间的显式依赖。

```python
class EdgeSpec(BaseModel):
    source_node: str
    source_port: str
    target_node: str
    target_port: str
```

### 设计要求

- 内部存储统一用显式边
- “按同名自动连线”只能作为 DSL 简写，不能作为最终存储格式

---

## 4.6 PipelineSpec

`PipelineSpec` 是测试流程的统一静态表示。

```python
class PipelineSpec(BaseModel):
    name: str
    version: str
    description: str = ""
    inputs: list[PortSpec]
    outputs: list[PortSpec]
    nodes: list[NodeSpec]
    edges: list[EdgeSpec]
    metadata: dict[str, Any] = {}
```

### 作用

- 执行引擎输入
- DOT / ONNX 导出输入
- 文档生成输入
- Schema 生成输入

### 最小保证

- 可静态检查
- 可拓扑排序
- 可导出

---

## 4.7 CaseSpec

`CaseSpec` 描述单个测试实例。

```python
class CaseSpec(BaseModel):
    case_id: str
    name: str
    pipeline: str
    inputs: dict[str, Any]
    expected: dict[str, Any] = {}
    tags: list[str] = []
    priority: str = "P2"
    timeout: int | None = None
    metadata: dict[str, Any] = {}
```

### MVP 建议

- 一个 `CaseSpec` 对应一个 `Pipeline`
- 多 Pipeline 组合执行放到 `TestSuite`

---

## 4.8 EnvProfile

`EnvProfile` 描述运行环境。

```python
class HostConfig(BaseModel):
    mode: str
    workdir: str | None = None
    docker_image: str | None = None


class DeviceConfig(BaseModel):
    protocol: str
    host: str
    port: int = 22
    user: str = "root"


class TransportPolicy(BaseModel):
    mode: str
    size_threshold_mb: int = 50


class EnvProfile(BaseModel):
    host: HostConfig
    device: DeviceConfig | None = None
    transport: TransportPolicy | None = None
    metadata: dict[str, Any] = {}
```

### 作用

- 将环境从算子逻辑中解耦
- 支持同一 Pipeline 在不同环境复用

---

## 5. Authoring 层设计

## 5.1 TestOp

`TestOp` 是开发者编写测试步骤的抽象基类。

建议职责:

- 持有 `OpSpec`
- 实现 `execute(step_context)`
- 可选实现 `validate / setup / teardown`

不建议职责:

- 自己管理环境连接
- 自己创建运行目录
- 自己决定执行顺序

---

## 5.2 Pipeline

`Pipeline` 是编写测试流程的 DSL 容器。

建议职责:

- 添加节点
- 连接边
- 定义 Pipeline 输入输出
- 生成 `PipelineSpec`

不建议:

- 直接作为最终执行 runtime
- 让任意 Python 逻辑成为不可导出的主路径

---

## 6. Runtime 层设计

## 6.1 ExecutionContext

`ExecutionContext` 描述一次 case 运行的全局上下文。

建议包含:

- `case_spec`
- `pipeline_spec`
- `env_profile`
- `run_dir`
- `artifact_store`
- `trace_recorder`
- `shared_data`

### 作用

- 贯穿整个 case 生命周期
- 负责统一目录、trace、日志和共享状态

---

## 6.2 StepContext

`StepContext` 描述单个 step 执行上下文。

建议包含:

- `node_spec`
- `step_dir`
- `inputs`
- `attrs`
- `logger`
- `host`
- `device`
- `transfer`
- `resource`
- `artifacts`

### 作用

- 限定算子可见范围
- 避免 `TestOp` 直接操作全局上下文

---

## 6.3 ResultSummary

`ResultSummary` 用于统一表达执行结论。

```python
class ResultSummary(BaseModel):
    case_id: str
    pipeline: str
    status: str
    started_at: str
    ended_at: str
    duration_ms: int
    outputs: dict[str, Any]
    failed_step: str | None = None
```

---

## 7. Infra 层设计

## 7.1 ActionRunner

`ActionRunner` 是所有副作用的统一入口。

负责:

- 执行动作
- 标准化结果
- 记录 trace
- 输出 stdout / stderr

### 不应由谁替代

- 不应由 `TestOp` 自己处理
- 不应由单个 Provider 私自决定日志格式

---

## 7.2 Executor / Transport / Resolver

建议将基础设施抽象为:

- `HostExecutor`
- `DeviceExecutor`
- `Transporter`
- `ResourceResolver`

共同特点:

- 可替换
- 可关闭
- 可 trace
- 可由 `EnvProfile` 配置驱动

---

## 8. 对象关系

可概括为:

```text
Pipeline/TestOp
    -> PipelineCompiler
    -> PipelineSpec/OpSpec
    -> TestEngine
    -> ExecutionContext/StepContext
    -> ActionRunner
    -> ArtifactStore/TraceRecorder
    -> ResultSummary
```

## 10. 设计结论

如果对象模型不先统一，后续最容易出现的问题是:

- Python / JSON / ONNX 三套模型并行
- 执行器和导出器理解不一致
- 文档和真实实现脱节

因此推荐优先实现顺序为:

1. `PortSpec / AttrSpec / OpSpec`
2. `NodeSpec / EdgeSpec / PipelineSpec`
3. `CaseSpec / EnvProfile`
4. `ExecutionContext / StepContext`
5. `ResultSummary`

这会为后续执行和追踪机制打下稳定基础。

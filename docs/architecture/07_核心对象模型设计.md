# 核心对象模型设计

本文档描述当前 TestPipe 的核心对象关系，重点覆盖 Authoring、Spec、Case 和 Execution 四层。

## 1. Authoring 层

作者写 Pipeline 时会直接接触：

- `Pipeline`
- `PipelineInputRef`
- `NodeHandle`
- `NodeOutputRef`
- `NodeDefinition`
- `OutputDefinition`

这一层的作用是“写图”。

## 2. Spec 层

编译后统一落到静态模型：

- `PipelineSpec`
- `NodeSpec`
- `InputBindingSpec`
- `EdgeSpec`
- `OutputBindingSpec`
- `PortSpec`
- `AttrSpec`
- `OpSpec`

这一层的作用是“让执行、校验、导图、文档生成都消费同一份结构”。

## 3. Case 层

YAML testcase 最终会被归一化为：

- `CaseSpec.inputs`
- `CaseSpec.inputs_by_node`
- `CaseSpec.expected`
- `CaseSpec.variables`

当前设计里：

- 流程级输入放进 `inputs`
- 节点专属输入放进 `inputs_by_node`

例如 `OnnxGitAtcPipeline`：

- `soc_version` 属于流程级输入
- `fetchModelNode.repo / ref / path` 属于节点直输输入

## 4. Execution 层

执行时核心对象包括：

- `ExecutionContext`
- `StepContext`
- `ResultSummary`
- `ArtifactStore`
- `TraceRecorder`

其中：

- `ExecutionContext` 持有 run 级状态
- `StepContext` 持有单节点执行期能力

## 5. 关键关系

### 5.1 Pipeline -> PipelineSpec

`PipelineCompiler` 负责把 Python DSL 编译成静态结构。

### 5.2 CaseSpec + PipelineSpec -> TestEngine

`TestEngine` 在执行时同时依赖这两份数据：

- `PipelineSpec` 决定图结构
- `CaseSpec` 决定当前 case 的具体输入值

### 5.3 执行结果 -> 图导出 / summary

节点输出和 pipeline 输出会同时用于：

- `summary.json`
- `pipeline_graph.dot`
- `pipeline_graph.pdf`

## 6. 当前与旧设计的差异

当前对象模型不再依赖：

- `forward()`
- `op_type`
- 运行时隐式图构建
- JSON/ONNX 作为主执行模型

当前统一以 `PipelineSpec` 为中心。

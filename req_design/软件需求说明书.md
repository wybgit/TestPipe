# TGE (AI NPU 测试图引擎) 架构设计需求规格书

## 1. 引言与定位 (Introduction)
Aegis-TGE (Test Graph Engine) 是一款专为端侧 NPU AI芯片（算子/模型转换与推理）设计的端到端测试验证框架。
框架核心定位如下：
*   **端到端与单点兼顾：** 支持从 Host 侧模型转换、编译，到 Device 侧资源拷贝、指令下发、结果回传与精度比对的全链路（Pipeline）场景，也可用于单算子功能测试。
*   **通信与环境统一调度：** 提供统一的 Host（本地/Docker）和 Device（SSH/Telnet）通信及环境管理能力。
*   **数据驱动驱动核心：** 彻底解耦“测试流程逻辑”与“测试用例数据”，使用例开发成本降至最低。
*   框架核心只承载用例的测试逻辑流程和环境交互、资源调度。

## 2. 核心设计哲学 (Design Philosophy)
本框架创造性地引入了 **AI编译器架构理念**：
1.  **测试即推理 (Test as Inference)：** 框架等价于推理引擎，测试流程（Pipeline）等价于模型构图（Graph），单步测试动作等价于算子（Op），测试用例等价于输入张量（Input Data）。
2.  **ONNX 原生图表达：** 借助 ONNX Protobuf 承载测试流程构图，可以借用 Netron 生态实现极致的图可视化。
3.  **大模型原生 (LLM-Native)：** 框架提供严格的输入/输出契约，只需大模型“填空”即可生成海量用例。
4.  **无感追踪与复现 (Transparent Tracing)：** 杜绝黑盒测试，执行时自动收集动作并生成底层可直接运行的 Bash 复现脚本。

## 3. 分层系统架构设计 (Architecture Layers)

框架自下而上分为四层结构：

### 3.1 基础设施层 (Infrastructure & Environment)
*   **全局配置解析：** 解析 `config.yaml` 或环境变量，定义 Host 编译机信息、Device 单板 IP、账号密码及挂载点。
*   **环境路由引擎 (Env Router)：** 抽象 `exec_cmd` 接口。若配置 Host 走 Docker 环境，则自动将当前工作目录挂载进容器内执行转换；否则在宿主机直接执行。
*   **智能存储与传输协议 (Smart Transporter)：**
    *   底层封装 `paramiko` 等协议。
    *   **自适应分流策略：** 小于阈值（如 50MB）的文件走 **SFTP** 传输；大于阈值的超大模型，自动切换为 **NFS** 策略（在 Host 端 copy 至共享目录，修改板端下发指令的路径直接读取挂载点），防止传输超时和单板存储容量不足。可以在配置文件中进行配置，启动路由还是全局配置。

### 3.2 测试算子层 (TestOp / Node Layer)
*   对基本动作进行 AW 封装（如：Git拉取、模型编译、资源下发、单板执行、Cosine比对）。
*   **契约注册制：** 每个 `TestOp` 必须使用类似 Pydantic `Field` 的语法，显式且严格地声明其 `Inputs` 和 `Outputs` 数据类型及说明。框架加载时进行严格约束检查，防止设计变形。

### 3.3 测试构图层 (TestGraph / Pipeline Layer)
*   将多个 `TestOp` 按依赖连线组装，形成执行流。
*   内置丰富的预设场景图（如 `StandardOpAccuracyGraph`, `ModelE2EGraph`），用户也可手动串联组装新图。
*   **拓扑检查：** 构图期静态检查依赖，数据流断裂直接报错。

### 3.4 会话执行引擎 (TestSession Runner)
*   负责加载测试图、解析用例输入数据，并驱动数据在各个 `TestOp` 节点间流转和断言。

## 4. 核心功能与实现细节 (Key Features & Implementation)

### 4.1 测试流的 ONNX 序列化与 Netron 可视化呈现
*   **机制：** 构图完成后，框架调用 `onnx` 库，将 `TestGraph` 转换为合法的 `Pipeline.onnx` 格式。
*   **映射关系：** `TestGraph` 对应计算图，`TestOp` 对应算子节点，传递的资源路径对应 Tensor，算子固有配置（如 timeout）对应 Attribute。
*   **用户侧体验：** 用户用浏览器打开 **Netron** 拖入该文件，即可看到一张带有数据流向、清晰标注了测试点和校验规则的可视化 DAG 图，完全替代复杂的文字流程说明。

### 4.2 隐式追踪 (Tracing) 与一键复现机制
*   **机制：** 抛弃繁琐的手工 Lowering 写法。`TestOp` 内的开发依然使用 Python 高级语法，但所有的底层交互必须通过 `Context` 上下文对象的挂载钩子（Hooks）执行（如 `context.run_shell()`, `context.device.run_cmd()`）。
*   **产出：** 框架后台会静默记录每一次底层调用，在测试执行完毕后，拼接生成一个绝对底层的 **`reproduce.sh` (bash脚本)**。用户拿着此脚本可脱离测试框架，在终端中一步步粘贴执行以 Debug 缺陷。

### 4.3 沙箱级工件隔离区 (Isolated Artifacts Workspace)
*   不再将日志混杂在控制台。针对每个独立测试用例（如用例ID: NPU_001），引擎运行时动态创建 `[CaseID]_[Timestamp]` 的独立文件夹。
*   **内部结构规范：**
    *   `spec.yaml`：该用例的输入参数快照。
    *   `reproduce.sh`：自动生成的 Bash 复现脚本。
    *   `step_01_Compile.log`, `step_02_Infer.log`：每一步算子执行的**独立级联日志**。
    *   `/data/`：存放过程产物（如拉取的模型文件、回传的断言结果）。

## 5. 用例编写规范与 AI 原生生态 (User Journey & LLM Native)

### 5.1 数据驱动的“填空式”用例编写
因为逻辑已沉淀在 `TestGraph` (ONNX) 中，测试用例文件仅需描述 **输入数据**。
*   **针对大模型 E2E 场景：** 使用 YAML 文件承载。
    ```yaml
    case_id: E2E_ResNet50_001
    graph_model: "Standard_E2E_Pipeline.onnx" # 指定Netron图
    inputs: # 参数名严格受图的 Inputs 约束
      model_git_url: "git@xxx.git"
      compile_soc: "Ascend310"
      golden_bin_path: "sftp://xxx/golden.bin"
    ```
*   **针对成百上千的算子用例：** 使用 CSV/Excel 承载。表头对应 Graph Inputs。执行引擎使用 `session.run_dataset("cases.csv")` 批量遍历执行。

### 5.2 大模型 (LLM) 一键用例生成
*   框架自带 CLI 工具 `aegis-tge export-schema`，自动提取所有 Node 和 Graph 的参数契约，导出为 JSON Schema 或 Markdown System Prompt。
*   将其喂给第三方 AI 模型，用户只需输入自然语言：“帮我测个Conv2D算子，输入维度是[1,3,224,224]”，大模型即可基于 Schema 零失误输出对应的 YAML 或 CSV 测试数据。

### 5.3 框架生态查阅网站
*   利用框架严格的强类型和装饰器契约，集成 `MkDocs`。
*   CI/CD 流水线每天自动抓取最新代码，生成带全局搜索的 API 静态网页（包含每个 TestOp 的功能描述、参数字典表、Netron截图）。新员工和用户可直接通过网站查阅现有框架能力。

## 6. 技术栈与部署约束
*   **编程语言：** Python 3.8+ (强依赖 Type Hinting 与 Pydantic 用于约束定义)。
*   **打包与分发：** 框架本身构建为 `.whl` 安装包，供测试业务仓通过 `pip install aegis-tge` 引用。
*   **日志规范：** 框架原生支持 `logging` 分级调整（如执行时传入 `--log-level=DEBUG` 可将 SSH 通信的每一条回显明文输出到 `step_xx.log` 中）。
*   **关键第三方库推荐：** `paramiko`/`fabric` (SSH/SFTP), `onnx` (图构建), `pydantic` (参数约束与Schema生成), `docker-py` (可选的Host侧容器操控)。
